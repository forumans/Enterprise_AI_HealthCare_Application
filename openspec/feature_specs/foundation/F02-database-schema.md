# F02 — Database Schema, Constraints, Triggers, Row-Level Security and Migrations

PostgreSQL 15+. This document gives the **target schema** — the state after the baseline plus migrations
001–008 — as one script a new build can apply, followed by the rules every feature relies on.

## 1. General data rules

- **DATA-GEN-01** Every primary key is a UUID generated by the database: `uuid_generate_v4()` (extension
  `uuid-ossp`).
- **DATA-GEN-02** Every business table except `tenants` carries `tenant_id uuid NOT NULL REFERENCES tenants(id)`.
  `audit_logs.tenant_id` is nullable (events without tenant context).
- **DATA-GEN-03** Every timestamp column is `timestamp with time zone` holding UTC. The backend SHALL refuse
  to start if any `public` column is `timestamp without time zone` (see F01 §5.2).
- **DATA-GEN-04** Every table has `created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`.
- **DATA-GEN-05 Soft delete.** Soft-deletable tables have `deleted_at timestamptz NULL` and
  `deleted_by uuid NULL REFERENCES users(id)`. Every read SHALL exclude `deleted_at IS NOT NULL` rows unless a
  feature says otherwise. Slots (`doctor_availability`) are hard-deleted; `audit_logs` is append-only.
- **DATA-GEN-06** The application binds only timezone-aware datetimes; a naive datetime from a client is
  treated as UTC.
- **DATA-GEN-07** Optional text inputs are trimmed and stored as NULL when empty (unless a feature states
  otherwise).
- **DATA-GEN-08** Emails are stored lower-cased and trimmed.

## 2. Enumerations

| Type | Values (order matters for `ALTER TYPE … ADD VALUE`) |
|------|--------|
| `user_role` | `ADMIN`, `DOCTOR`, `PATIENT`, `SUPPORT_STAFF` |
| `appointment_status` | `SCHEDULED`, `CONFIRMED`, `CANCELLED`, `COMPLETED` |
| `slot_status` | `AVAILABLE`, `BOOKED`, `BLOCKED` |
| `gender_type` | `MALE`, `FEMALE`, `OTHER`, `PREFER_NOT_TO_SAY` (exists for reference; `patients.gender` is `varchar(20)` holding one of these values) |

## 3. Entity relationships

```
tenants 1───* users 1───1 { patients | doctors | support_staff | admins }   (by users.role)
doctors 1───* doctor_availability (slots)
doctors 1───* appointments *───1 patients
appointments *───0..1 doctor_availability   (slot_id, composite FK with tenant_id)
appointments 1───0..1 medical_records 1───0..1 prescriptions *───0..1 pharmacies
patients 1───* patient_documents
users 1───* audit_logs (performed_by)
```

```sql
CREATE TYPE appointment_status AS ENUM ('SCHEDULED', 'CONFIRMED', 'CANCELLED', 'COMPLETED');

    doctor_id    uuid NOT NULL REFERENCES doctors(id) ON DELETE CASCADE,

    tenant_id        uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    doctor_id        uuid NOT NULL REFERENCES doctors(id) ON DELETE CASCADE,
    patient_id       uuid NOT NULL REFERENCES patients(id) ON DELETE CASCADE,
    slot_id          uuid REFERENCES doctor_availability(id) ON DELETE CASCADE,
    appointment_time timestamptz NOT NULL,                 -- equals the slot's slot_time
    status           appointment_status NOT NULL DEFAULT 'SCHEDULED',
    notes            text,                                 -- the visit reason
    created_at       timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at       timestamptz,
    deleted_by       uuid REFERENCES users(id),
    CONSTRAINT fk_slot_tenant FOREIGN KEY (slot_id, tenant_id)
        REFERENCES doctor_availability (id, tenant_id) ON DELETE CASCADE
);
CREATE INDEX idx_appointments_doctor  ON appointments (doctor_id);
CREATE INDEX idx_appointments_patient ON appointments (patient_id);
CREATE INDEX idx_appointments_time    ON appointments (appointment_time);
-- A doctor can't have two live appointments at once; neither can a patient (with any doctor)
CREATE UNIQUE INDEX unique_doctor_time  ON appointments (doctor_id,  appointment_time) WHERE status <> 'CANCELLED';
CREATE UNIQUE INDEX unique_patient_time ON appointments (patient_id, appointment_time) WHERE status <> 'CANCELLED';

CREATE TABLE medical_records (
    id             uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id      uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    appointment_id uuid NOT NULL UNIQUE REFERENCES appointments(id) ON DELETE CASCADE,  -- 1 per appointment
    symptoms       text,                                   -- API field name: "notes"
    diagnosis      text,
    lab_results    text,
    created_at     timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at     timestamptz,
    deleted_by     uuid REFERENCES users(id)
);
CREATE INDEX idx_medical_records_tenant ON medical_records (tenant_id);

CREATE TABLE pharmacies (                                  -- reference data, seeded per tenant; no UI
    id          uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id   uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    name        varchar(255) NOT NULL,
    address     text,
    phone       text,
    created_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at  timestamptz,
    deleted_by  uuid REFERENCES users(id)
);

CREATE TABLE prescriptions (
    id                 uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id          uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    medical_record_id  uuid NOT NULL UNIQUE REFERENCES medical_records(id) ON DELETE CASCADE, -- 1 per record
    pharmacy_id        uuid REFERENCES pharmacies(id) ON DELETE SET NULL,
    medication_details text NOT NULL,       -- "<medication> - <dosage>. <instructions or 'Take as prescribed'>"
    created_at         timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at         timestamptz,
    deleted_by         uuid REFERENCES users(id)
);
CREATE INDEX idx_prescriptions_tenant ON prescriptions (tenant_id);

CREATE TABLE patient_documents (
    id            uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id     uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    patient_id    uuid NOT NULL REFERENCES patients(id) ON DELETE CASCADE,
    document_name varchar(255),          -- sanitized original file name
    document_type varchar(100),          -- MIME type
    file_path     text,                  -- S3 key documents/<tenant>/<patient>/<yyyymmddHHMMSS>_[<uploader>_]<name>
    signed_at     timestamptz,           -- reserved for e-signature
    created_at    timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at    timestamptz,
    deleted_by    uuid REFERENCES users(id)
);

CREATE TABLE audit_logs (                                  -- append-only
    id           uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id    uuid REFERENCES tenants(id),
    table_name   text NOT NULL,
    record_id    uuid NOT NULL,
    action_type  varchar(32) NOT NULL,   -- INSERT | UPDATE | DELETE | READ (application access events)
    old_data     jsonb,
    new_data     jsonb,
    performed_by uuid REFERENCES users(id),
    performed_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE rate_limit_events (                           -- migration 009; no tenant_id, no RLS
    id          uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    limit_name  varchar(32) NOT NULL,                      -- login-email, login-ip, reset-email, reset-ip, register-ip
    key_hash    char(64) NOT NULL,                         -- SHA-256 of the lower-cased email or client address
    created_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_rate_limit_events_key ON rate_limit_events (limit_name, key_hash, created_at);
CREATE INDEX idx_rate_limit_events_created ON rate_limit_events (created_at);
```

## 5. Triggers

### 5.1 `sync_doctor_availability` (AFTER INSERT OR UPDATE OR DELETE ON appointments, FOR EACH ROW)

As rewritten by migration 010 (the release rule, `DATA-TRG-02`):

```sql
CREATE OR REPLACE FUNCTION sync_doctor_availability() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN                               -- book; block_id is kept
        UPDATE doctor_availability SET status = 'BOOKED'
         WHERE doctor_id = NEW.doctor_id AND slot_time = NEW.appointment_time;
        RETURN NEW;
    END IF;
    IF TG_OP = 'UPDATE' THEN                               -- the change INTO CANCELLED releases the slot
        IF NEW.status = 'CANCELLED' AND OLD.status IS DISTINCT FROM 'CANCELLED' THEN
            UPDATE doctor_availability
               SET status = CASE WHEN block_id IS NOT NULL THEN 'BLOCKED' ELSE 'AVAILABLE' END::slot_status,
                   block_reason = CASE WHEN block_id IS NOT NULL THEN block_reason END
             WHERE doctor_id = NEW.doctor_id AND slot_time = NEW.appointment_time AND status = 'BOOKED';
        END IF;
        RETURN NEW;
    END IF;
    IF TG_OP = 'DELETE' THEN                               -- deleting a live appointment releases the slot
        IF OLD.status IS DISTINCT FROM 'CANCELLED' THEN
            UPDATE doctor_availability
               SET status = CASE WHEN block_id IS NOT NULL THEN 'BLOCKED' ELSE 'AVAILABLE' END::slot_status,
                   block_reason = CASE WHEN block_id IS NOT NULL THEN block_reason END
             WHERE doctor_id = OLD.doctor_id AND slot_time = OLD.appointment_time AND status = 'BOOKED';
        END IF;
        RETURN OLD;
    END IF;
    RETURN NULL;
END $$;
CREATE TRIGGER trg_sync_availability AFTER INSERT OR UPDATE OR DELETE ON appointments
    FOR EACH ROW EXECUTE FUNCTION sync_doctor_availability();
```

Before 010 (migration 002) cancel and delete always set the slot `AVAILABLE`; `010_schedule_blocks_rollback.sql`
restores that version.

- **DATA-TRG-01** The trigger does **not** react to a change of `appointment_time`. Rescheduling SHALL free the
  old slot (by the release rule) and book the new one in application code
  ([07](../features/07-appointment-lifecycle.md)).
- **DATA-TRG-02 Release rule.** A slot freed by cancelling, deleting or moving its appointment becomes `BLOCKED`
  (keeping its `block_reason`) when it has a `block_id`, and `AVAILABLE` (reason cleared) otherwise — in the same
  transaction, so a blocked hour is never bookable in between ([08](../features/08-doctor-availability.md)
  `BR-SLOT-19`). Only a `BOOKED` slot is released, and only on the change into `CANCELLED`, so editing or deleting
  an already-cancelled appointment never frees a slot someone has booked since.
- Booking also sets the slot `BOOKED` in application code in the same transaction (idempotent with the trigger).

### 5.2 `audit_trigger_function` (database-level full-row trail)

```sql
CREATE OR REPLACE FUNCTION audit_trigger_function() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE v_user uuid; v_tenant uuid;
BEGIN
    BEGIN v_user   := current_setting('app.current_user_id')::uuid; EXCEPTION WHEN OTHERS THEN v_user := NULL; END;
    BEGIN v_tenant := current_setting('app.current_tenant')::uuid;  EXCEPTION WHEN OTHERS THEN v_tenant := NULL; END;
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_logs (tenant_id, table_name, record_id, action_type, new_data, performed_by)
        VALUES (v_tenant, TG_TABLE_NAME, NEW.id, 'INSERT', to_jsonb(NEW), v_user); RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit_logs (tenant_id, table_name, record_id, action_type, old_data, new_data, performed_by)
        VALUES (v_tenant, TG_TABLE_NAME, NEW.id, 'UPDATE', to_jsonb(OLD), to_jsonb(NEW), v_user); RETURN NEW;
    ELSE
        INSERT INTO audit_logs (tenant_id, table_name, record_id, action_type, old_data, performed_by)
        VALUES (v_tenant, TG_TABLE_NAME, OLD.id, 'DELETE', to_jsonb(OLD), v_user); RETURN OLD;
    END IF;
END $$;
```

Attached `AFTER INSERT OR DELETE OR UPDATE … FOR EACH ROW` as `audit_<table>` on: `users`, `patients`, `doctors`,
`support_staff`, `appointments`, `medical_records`, `prescriptions`, `pharmacies`, `patient_documents`,
`schedule_blocks` (migration 010)
(trigger on `patient_documents` is named `audit_documents`). Not on `tenants`, `admins`,
`doctor_availability` or `audit_logs`. This trail is in addition to the application audit entries (F04).

## 6. Row-level security (`DATA-RLS`, migration 007)

```sql
CREATE OR REPLACE FUNCTION app_current_tenant() RETURNS uuid LANGUAGE sql STABLE AS
$$ SELECT NULLIF(current_setting('app.current_tenant', true), '')::uuid $$;

-- For each of: users, patients, doctors, support_staff, admins, doctor_availability, appointments,
--              medical_records, prescriptions, pharmacies, patient_documents, audit_logs,
--              schedule_blocks (added by migration 010)
ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <t>
    USING (tenant_id = app_current_tenant()) WITH CHECK (tenant_id = app_current_tenant());
```

- **DATA-RLS-01** With no `app.current_tenant` set, tenant tables appear empty to the app user. `tenants` has no
  RLS.
- **DATA-RLS-02** The backend sets `app.current_tenant` and `app.current_user_id` with
  `SELECT set_config('app.current_tenant', :t, true), set_config('app.current_user_id', :u, true)`
  (transaction-local) **at the start of every transaction** (SQLAlchemy `Session` `after_begin` event), from the
  verified token, or — on public endpoints — from the tenant the endpoint resolved (`set_db_tenant`) (F03).
- **DATA-RLS-03 Cross-tenant lookups** are the only reads that ignore the tenant, and go only through these
  `SECURITY DEFINER` functions (`SET search_path = pg_catalog, public`, `EXECUTE` revoked from `PUBLIC`, granted
  to the app user):

```sql
app_login_lookup(p_email text) RETURNS TABLE (id uuid, tenant_id uuid, role user_role, password_hash text)
  -- WHERE email = lower(p_email) AND deleted_at IS NULL AND is_active  LIMIT 1
app_reset_lookup(p_user_id uuid) RETURNS TABLE (id, tenant_id, role, password_hash)
  -- WHERE id = p_user_id AND deleted_at IS NULL AND is_active
app_email_in_use(p_email text, p_tenant uuid, p_exclude uuid) RETURNS boolean
  -- EXISTS user with email = lower(p_email) AND (deleted_at IS NULL OR tenant_id = p_tenant)
  --        AND (p_exclude IS NULL OR id <> p_exclude)
app_any_active_admin() RETURNS boolean
  -- EXISTS user with role = 'ADMIN' AND is_active AND deleted_at IS NULL (any tenant)
```

- **DATA-RLS-04** The app's DB user (`healthcare_user`) SHALL NOT own the tables nor have `BYPASSRLS`. The owner
  (RDS master) and superusers are not restricted (no `FORCE ROW LEVEL SECURITY`), so migrations, backups and the
  functions above work.
- **DATA-RLS-05** If the functions don't exist (007 not applied), the backend runs the same lookups as plain
  queries (checked once with `to_regprocedure('public.app_login_lookup(text)')`), so code and migration deploy in
  either order.

## 7. Privileges (migration 006)

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO healthcare_user;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO healthcare_user;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO healthcare_user;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO healthcare_user;
```

The app connects as `healthcare_user` (DML only). Migrations run as the owner.

- **DATA-MIG-01** Migrations are numbered `NNN_description.sql`, idempotent (`IF NOT EXISTS`, guarded `DO`
  blocks), wrapped in `BEGIN … COMMIT`, and run with `psql -v ON_ERROR_STOP=1`.
- **DATA-MIG-02** A migration SHALL be applied before the backend version that needs it; migrations SHOULD be
  backward compatible with the running backend (expand first, contract in a later release).
- **DATA-MIG-03** When a feature needs a migration that isn't applied, the API SHOULD return a clear 503 naming
  it (example: creating support staff before 005 —
  "Support staff accounts aren't available yet: the database needs migration 005_add_support_staff_role.sql.").
- **DATA-MIG-04** A schema snapshot SQL (`aws_env_spin_up/scripts/schema_snapshot.sql`) and comparer
  (`compare_schema.py`) SHALL cover tables, columns, enums, indexes, triggers, functions and RLS policies so the
  cloud and local schemas can be diffed. The snapshot also lists `migrations_applied` (005, 007–010, each
  recognised by an object it creates), so the comparer shows which migrations each side is missing.

## 9. Seed and reference data

- **DATA-SEED-01** Clinics are created by the platform operator (SQL or seed script) with `name`, `domain` (the
  host their site is served on) and `timezone`. There is no tenant-creation API.
- **DATA-SEED-02** On a brand-new deployment with no tenant, the first public registration creates
  `Tenant(name="Default Tenant", domain="default.local", timezone=CLINIC_TIMEZONE)` ([04](../features/04-patient-self-registration.md)).

## 10. Status and slot model summary (used by many features)

| Slot status | Meaning | Set by |
|-------------|---------|--------|
| `AVAILABLE` | Open for booking | default generation; add / unblock (single or range); cancellation (trigger) or reschedule (old slot) of a slot **without** `block_id` |
| `BOOKED` | Held by a live appointment | booking (code + trigger); reschedule (new slot) |
| `BLOCKED` | Not bookable, optional `block_reason` | doctor or support staff (single slot or range block); cancellation or reschedule of a slot **with** `block_id` (DATA-TRG-02) |

A `BOOKED` slot with a `block_id` is an appointment that **needs rescheduling** (the doctor blocked the hour after
it was booked); the flag is derived, never stored on the appointment ([16](../features/16-support-appointments.md)).

| Appointment status | Meaning |
|--------------------|---------|
| `SCHEDULED` | Booked, not yet confirmed (initial) |
| `CONFIRMED` | Confirmed by the doctor; consultation allowed |
| `COMPLETED` | Consultation saved (terminal) |
| `CANCELLED` | Cancelled; row also soft-deleted (terminal) |
