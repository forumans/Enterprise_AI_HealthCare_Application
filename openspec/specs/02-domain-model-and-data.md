# 02 — Domain Model and Data

## 1. General data rules

- **DATA-GEN-01** Every primary key SHALL be a UUID generated by the database (`uuid_generate_v4()`).
- **DATA-GEN-02** Every business table except `tenants` SHALL have `tenant_id uuid NOT NULL REFERENCES tenants(id)`.
  `audit_logs.tenant_id` is nullable for events that have no tenant context.
- **DATA-GEN-03** Every timestamp column SHALL be `timestamp with time zone` (TIMESTAMPTZ) and hold UTC.
  The backend SHALL refuse to start if any `public` column is still `timestamp without time zone`, and name
  the offending columns in the error.
- **DATA-GEN-04** Every table SHALL have `created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`.
- **DATA-GEN-05** Soft-deletable tables SHALL have `deleted_at timestamptz NULL` and
  `deleted_by uuid NULL REFERENCES users(id)`. Every read SHALL exclude rows where `deleted_at IS NOT NULL`
  unless the requirement says otherwise.
- **DATA-GEN-06** The application SHALL bind only timezone-aware datetimes. A naive datetime received from a
  client SHALL be treated as UTC.
- **DATA-GEN-07** Schema changes SHALL be delivered as numbered SQL migration files
  (`NNN_description.sql`) that are idempotent and safe to re-run. There is no ORM migration tool.
  `DB_SCHEMA_INIT_ON_STARTUP=true` (ORM `create_all`) is allowed only for local development.

## 2. Enumerations (PostgreSQL enum types)

| Type | Values |
|------|--------|
| `user_role` | `ADMIN`, `DOCTOR`, `PATIENT`, `SUPPORT_STAFF` |
| `appointment_status` | `SCHEDULED`, `CONFIRMED`, `CANCELLED`, `COMPLETED` |
| `slot_status` | `AVAILABLE`, `BOOKED`, `BLOCKED` |
| `gender_type` | `MALE`, `FEMALE`, `OTHER`, `PREFER_NOT_TO_SAY` (the column `patients.gender` is `varchar(20)` holding these values) |

## 3. Entity relationship overview

```
tenants 1───* users 1───1 { patients | doctors | support_staff | admins }   (one profile per user, by role)
doctors 1───* doctor_availability (slots)
doctors 1───* appointments *───1 patients
appointments *───0..1 doctor_availability (slot_id)
appointments 1───0..1 medical_records 1───0..1 prescriptions *───0..1 pharmacies
patients 1───* patient_documents
users 1───* audit_logs (performed_by)
```

## 5. Database triggers

- **DATA-TRG-01 `sync_doctor_availability`** (AFTER INSERT OR UPDATE OR DELETE on `appointments`, per row):
  - INSERT → set the matching slot (`doctor_id`, `slot_time = appointment_time`) to `BOOKED`;
  - UPDATE with `NEW.status = 'CANCELLED'` → set the matching slot to `AVAILABLE`;
  - DELETE → set the matching slot to `AVAILABLE`.
  It does not react to a change of `appointment_time`; rescheduling SHALL free and book slots in application
  code (see `BR-APT-RESCHED`).
- **DATA-TRG-02 `audit_trigger_function`** (AFTER INSERT OR UPDATE OR DELETE) on `users`, `patients`, `doctors`,
  `support_staff`, `appointments`, `medical_records`, `prescriptions`, `pharmacies`, `patient_documents`:
  writes a full-row `audit_logs` entry (`to_jsonb(OLD/NEW)`), reading actor and tenant from the session
  settings `app.current_user_id` and `app.current_tenant` (NULL when unset). This is a database-level safety
  net alongside the application-level audit entries in `SEC-AUD`.

## 6. Migrations (history and purpose)

| File | Purpose |
|------|---------|
| baseline schema | Extensions, enums, tables, constraints, indexes, triggers above (without `SUPPORT_STAFF`) |
| `001_add_patient_and_availability_fields.sql` | Drops legacy `is_booked`; adds `block_reason`; adds patient DOB, gender and address columns |
| `002_fix_sync_function.sql` | Recreates `sync_doctor_availability` to use `status` |
| `003_convert_timestamps_to_timestamptz.sql` (+ rollback) | Converts every timestamp column to TIMESTAMPTZ, interpreting existing values as UTC |
| `004_backfill_evening_availability_slots.sql` | One-time backfill of 5 PM–11 PM slots after office hours were extended (DST-safe, clinic zone configurable) |
| `005_add_support_staff_role.sql` | Adds `SUPPORT_STAFF` to `user_role`; creates `support_staff` with its audit trigger (idempotent; no rollback since enum values cannot be removed) |
| `006_grant_app_user_access.sql` | Grants the app database user DML on all tables and sequences and sets default privileges for future tables |

- **DATA-MIG-01** A migration SHALL be applied before the backend version that needs it is deployed.
- **DATA-MIG-02** The application SHALL connect as a non-owner database user with only SELECT, INSERT,
  UPDATE and DELETE privileges. Migrations run as the owner (master) user.
- **DATA-MIG-03** If a feature depends on a migration that has not been applied, the API SHOULD return a clear
  503 message naming the migration (as admin creation of support staff does before migration 005), not a raw
  database error.
- **DATA-MIG-04** Migrations SHOULD be backward compatible with the backend version currently running
  (expand first — add nullable columns, new tables, new enum values — and remove old structures only in a later
  release), so a migration can be applied before the new code is deployed without an outage.

## 7. Seed and reference data

- **DATA-SEED-01** On first use, if no tenant exists, the public registration endpoints SHALL create a
  default tenant (`name = "Default Tenant"`, `domain = "default.local"`). Self-registered users join the
  first tenant (see doc 13 on multi-tenant onboarding).
- **DATA-SEED-02** Pharmacies SHALL be seeded per tenant. The consultation form handles an empty list.
- **DATA-SEED-03** A deterministic, idempotent seed script SHOULD create a development tenant with one user per
  role, a few doctors with slots, patients, appointments in each status and pharmacies, using fictitious data
  only. Tests SHALL create their own data and never depend on the development seed.
